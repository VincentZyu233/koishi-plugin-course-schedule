## 三、实施计划

### 第一阶段：扩展导入格式（3 个新 parser）

**目标：让用户能用更多来源导入课表**

#### 1.1 星链课表 API 解析

- **新文件**：`src/services/starlink-parser.ts`
- **API 端点**：`https://api.starlinkkb.cn/share/curriculum/{code}`
- **触发方式**：
  - `课表.绑定` 检测到 `「星链课表」` 关键词
  - 或直接传入分享码
- **数据格式**：课程含 `startSection` / `endSection` / `weekday` 字段，需配合 `timeSlots` 映射为实际时间
- **转换逻辑**：
  1. 请求 API 获取 JSON
  2. `convertStarlinkJsonToStandard()` — 节次号 → 时间映射
  3. 合并连续课程（同一名称、同一地点、相邻节次）
  4. 输出标准 `CourseRecord[]`

#### 1.2 拾光课表 JSON + 原生 JSON 解析

- **新文件**：`src/services/json-parser.ts`
- **触发方式**：
  - `课表.绑定` 收到 `.json` 文件附件
  - 或粘贴 JSON 文本
- **格式检测**：
  - 拾光格式：课程含 `startSection` / `endSection` 或 `isCustomTime`，且包含 `timeSlots` 数组
  - 原生格式：课程含 `startTime` / `endTime` / `day` / `weeks`
- **转换逻辑**：
  1. 检测格式类型
  2. 拾光：`timeSlotMap` 节次号 → 实际时间
  3. 原生：直接映射
  4. 输出标准 `CourseRecord[]`

#### 1.3 WakeUp 备份文件 `.wakeup_schedule` 解析

- **新文件**：`src/services/wakeup-file-parser.ts`
- **触发方式**：`课表.绑定` 收到 `.wakeup_schedule` 文件
- **文件格式**：多行 JSON（每行一个对象，共 5 个）：
  1. 时间元数据
  2. 节次时间条目（节次号 → startTime/endTime）
  3. 课表元数据（含 `startDate`、`tableName`）
  4. 课程定义（id → courseName）
  5. 课程安排（含 `id`、`day`、`startNode`、`step`、`startWeek`、`endWeek`、`type`）
- **周次类型**：`type: 0` = 每周，`type: 1` = 单周，`type: 2` = 双周
- **转换逻辑**：
  1. 逐行解析 JSON
  2. 构建节次时间映射
  3. 关联课程定义和课程安排
  4. 计算周次数组
  5. 输出标准 `CourseRecord[]`

#### 1.4 bind.ts 路由逻辑升级

- **修改文件**：`src/commands/bind.ts`
- **改动**：在现有 WakeUp / ICS 检测基础上，增加：
  - 检测 `「星链课表」` → 走 starlink-parser
  - 检测 `.json` 文件附件 → 走 json-parser
  - 检测 `.wakeup_schedule` 文件附件 → 走 wakeup-file-parser
  - 检测 JSON 文本（`BEGIN:VCALENDAR` 以外的 `{` 开头）→ 走 json-parser

### 第二阶段：新视图 + 节假日

#### 2.1 周课表（7 天纵览）

- **新文件**：`src/commands/week.ts`、`src/render/weekly-template.ts`
- **命令**：`课表.周课表` / `课表.周课表 [dayOffset]`
- **布局**（参考 `weekly-schedule-template.html`）：
  - 7 列网格（周一到周日），每列显示当天所有课程
  - 每门课程显示：时间、名称、地点
  - 标题：`周课表 · YYYY/MM/DD - YYYY/MM/DD`
- **数据来源**：`ScheduleService.renderWeeklySchedule(channelId, userid, dayOffset)`
- **渲染**：Puppeteer 截图，同现有模板风格

#### 2.2 中国节假日数据

- **新文件**：`src/services/holiday.ts`、`src/constants/holidays.ts`
- **数据格式**：
  ```typescript
  interface HolidayData {
    year: number
    holidays: { date: string; name: string; type: 'holiday' | 'workday' }[]
  }
  ```
- **用途**：
  - 群课表/个人课表：节假日显示"休息日"，调休上班日显示"调休上班"
  - 周课表：跳过节假日列或标记
  - 推送通知（后续）：节假日不发推送
- **2026 年数据**：元旦、春节（除夕至初七）、清明节、劳动节、端午节、中秋节、国庆节 + 调休上班日

### 第三阶段：增强功能

#### 3.1 调课/撤销调课

- **新文件**：`src/commands/reschedule.ts`
- **命令**：
  - `课表.调课 <原日期> <新日期>` — 将某天的课程调到另一天
  - `课表.撤销调课 <日期>` — 撤销某次调课
- **逻辑**：
  1. 查找原日期的课程
  2. 创建新课程对象（标记 `rescheduled: true`，记录 `originalDay`/`originalWeek`/`originalDate`）
  3. 从原课程的 `weeks` 数组中移除该周
  4. 如果新日期已有课程，询问用户是否**调换**两天
  5. 撤销时根据 `originalDay`/`originalWeek` 匹配回溯

#### 3.2 自定义节次时间表

- **新文件**：`src/services/time-table.ts`
- **命令**：
  - `课表.设置时间表` — 上传/更新时间表 JSON
  - `课表.更新时间表` — 从星链/拾光分享更新时间
- **逻辑**：
  1. 解析时间表 JSON（支持 4 种格式）
  2. 存储到用户配置（`course_schedule_time_table` 表或 JSON 文件）
  3. 渲染时优先使用自定义时间表
  4. 节次重建：通过 5 分钟容差窗口将开始/结束时间匹配回节次号

## 四、数据模型扩展

### 当前 `CourseRecord`

```typescript
interface CourseRecord {
  id: number
  channelId: string
  userid: string
  username: string
  useravatar: string
  curriculumndate: string[]    // 星期数组 ['周一', '周二', ...]
  curriculumname: string
  curriculumtime: string       // "HH:MM-HH:MM"
  startDate: string            // "YYYY-MM-DD"
  endDate: string              // "YYYY-MM-DD"
  location?: string
  source?: 'ics' | 'wakeup' | 'manual'
}
```

### 需要新增的字段

```typescript
interface CourseRecord {
  // ... 现有字段 ...
  source?: 'ics' | 'wakeup' | 'starlink' | 'shiguang' | 'wakeup-file' | 'json' | 'manual'
  weeks?: number[]             // 上课周次（可选，用于周课表和调课）
  startNode?: number           // 起始节次号（用于时间表重建和导出）

  teacher?: string             // 教师姓名
  rescheduled?: boolean        // 是否调课课程
  originalDay?: number         // 调课前原本是星期几
  originalWeek?: number        // 调课前原本是第几周
  originalDate?: string        // 调课前原本日期的可读描述
}
```

## 六、风险和注意事项

1. **数据库迁移**：新增 `weeks`、`startNode`、`step`、`teacher` 等字段需要兼容旧数据（查询时给默认值）
2. **节假日数据**：每年需要更新 `holidays.ts`，可考虑从 API 拉取或手动维护
3. **星链 API**：`api.starlinkkb.cn` 可能有速率限制，需处理超时和错误
4. **WakeUp 备份文件**：`.wakeup_schedule` 格式可能随 WakeUp 版本变化，需保持兼容
5. **调课冲突**：需要用户交互（询问是否调换），在群聊场景下体验可能不佳
6. **推送通知**：需要 Koishi 定时任务支持，且需要用户授权（加好友或群内 @）
