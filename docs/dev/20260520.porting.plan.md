# 课程表插件迁移计划

目标：把 `nonebot-plugin-course-schedule` / `astrbot_plugin_CourseSchedule` 的课程表能力迁移到 Koishi 版 `course-schedule`，并结合现有 Koishi 插件 `curriculum-table` 的实现经验，做出一个更适合 Koishi 的新插件方案。

核心取向：功能结构参考 `curriculum-table`，但页面视觉与出图风格更靠近 AstrBot 版，不沿用当前 `curriculum-table` 那种偏“列表卡片”的 UI。

## 迁移原则

1. 先拆纯逻辑，再接 Koishi 命令层。
2. 绑定、解析、渲染、排行、提醒分层，不要把业务塞进 `src/index.ts`。
3. 兼容 `.ics` 和 WakeUp 导入逻辑，尽量保留原始数据语义，方便老用户迁移。
4. UI 走“课程表感”而不是“消息列表感”：更像 AstrBot 的出图，但保留 Koishi 插件常见的稳定命令和数据模型。
5. 先做可用版：绑定课表、查看个人课表、查看群友课表、上课排行；提醒和定时推送放第二阶段。

## 参考结论

### 来自 AstrBot 版的价值

- `main.py` 里的主流程更接近“绑定 -> 解析 -> 落库/落盘 -> 出图”的真实链路。
- `ics_parser.py` 里对 `.ics` / WakeUp 的处理是核心资产，应该优先迁移。
- `image_generator.py` 的单独渲染层适合继续保留，并重写成 TS 服务。
- `schedule_helper.py` 的个人/群友筛选逻辑可以直接变成 Koishi service。

### 来自 `curriculum-table` 的价值

- `src/index.ts` 已经验证了 Koishi 的命令注册、数据库表、定时任务接法。
- `src/render.ts` 证明了 Koishi 里用 `puppeteer + template` 做出图是可行的。
- `src/commands/*` 的拆分方式很适合后续维护。
- 但它的当前 UI 更偏“群友列表卡片”，不符合这次想要的课程表视觉方向，所以只能借结构，不直接照搬样式。

## 命令规划

- `绑定课表`：支持 `.ics` 文件和 WakeUp 口令。
- `解绑课表`：移除用户全部绑定。
- `绑定群聊课表` / `退出群聊课表`：保留群内展示开关。
- `课表` / `查看课表`：查看个人课表，支持 `今天/明天/周三/偏移量`。
- `群课表`：查看群友课表，优先出“当前正在上/下一节”。
- `上课排行`：统计本周时长和节数。

## 出图方向

1. 课程表图片不要做成纯表格，优先做成“有层次的课程卡片”。
2. 保留 AstrBot 那种更强的标题、状态块、时间块、地点块表达。
3. Koishi 现有 `curriculum-table` 的 `template + puppeteer` 架构可以复用，但模板样式要重写。
4. 如果要保留“按人/按时间”两种模式，也建议放成配置项，而不是把它当 UI 主轴。

## 落地步骤

1. 先把 ICS 解析、WakeUp 转换、数据持久化迁到 TS。
2. 再把个人课表、群课表、排行这三条命令接到 Koishi。
3. 然后补日期解析能力，把“昨天/明天/周三/偏移量”统一成一个工具。
4. 再重写模板和样式，让出图更接近 AstrBot 版。
5. 最后再做提醒任务、定时推送和缓存优化。

## 需要注意的坑

- AstrBot 的事件对象和 Koishi 的 `Session` 不一样，不能硬搬 handler。
- `curriculum-table` 依赖数据库表结构，迁移时要决定是继续用数据库还是改成文件存储。
- 图片生成依赖字体和头像下载，TS 版要提前约定资源目录和失败回退。
- `rrule` / `ics` 的时区和周跨天处理要单独验收，避免课表错位。
- WakeUp 导入和 `.ics` 导入最好收敛到同一个 service，避免后续出现两套逻辑。

## 结论

这次迁移最稳的方式，不是直接翻 `main.py`，也不是直接复用现成 `curriculum-table` 的 UI，而是把 AstrBot 的业务链路抽出来，再借 Koishi 插件的目录和命令组织方式重做一版。这样功能、风格、维护性三者都能兼顾。
